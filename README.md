How do I interpret user needs and implement them into a program? How does creating “user stories” help with this?

By listening to the user or client, I can find out what the user needs the program to do. And by turning these needs into a user story, I can implement those needs into a feature in a program. An by parsing the user story as: "As an _____, I want to be able to ______ by doing _______." I can undersatnd and express what the user wants or needs the program to do, and write code that makes that feature happen. As I understand it, each user story should express one need, want or desire of the end user or client, a larger combined story may be an Epic, which will give an overview of functions grouped together, and after it is refined, it will be broken down to indiviual Stories.


How do I approach developing programs? What Agile processes do I hope to incorporate into my future development work?

When I am developing a program I first assess what the needs, wants, and desires are for the program. I like to ask "What is it supposed to do?". If there is existing code, I will read through the code and the comments, to see what the existing code already does. Once I have an idea of what the  program is supposed to do, and what any exisiting code is supposed to do, I like to break down each new function or feature into individual steps, and then code the steps, and testing thecode every line or two, at a reasonable break point, to make sure it works as expected. Once I get the indivual steps coded, I will then apply them as a function to whatever input data is given, and see what happens whan I runthe program. If things go well, life is good, but usually I have made an error somewhere along the line, so I start diagnosing what went wrong, and fixing the code until it works as expected. I often spend as much time researching the code syntax to make sure I have written it correctly as I do writitng the code itself, I find that I need to research the individual finctions to find out how to acheive operation X in as few a number of steps as possible. For instance if I wanted to find the nearest whole number from the result of a sqaure root, rounded down, I could use round, a floor function, or turn the value into an integer from a double, in each case I would be processing the data in a specific way for a specific reason, and would need to apply specific syntax to make the process work properly. 
  As I progress through my career I hope to be able to implemenet some of the Agile processes in my furtur work. I like the idea of Kanban boards to track what needs to be done, what is getting done ,and what has been done, in a visible manner. Something I have already used, and called it something different is the Daily Scrum. What I used to do was hold a meeting with my crew every moring, to make sure we got everything done the day before, assign work for the day, and giver an overview of where we were in the project, and if we needed to push harder to make milestones or deadlines. I am also a fan of letting people choose thier own work assignements, as they will pick the one they feel most suited for and will do a better job than someone who has been given "the worst job", in their opinion. I also think I'l try to be mindful of the idea of minimally working code, meaning that I will write code that meets the requirements minimally, and hopefully its simplicity will keep it from breaking later when it is integrated with a larger system. 

What does it mean to be a good team member in software development?

I think this might be the toughest question I have been asked in a while. In my mind being a good team member is to be someone who will pull their weight, take on tasks they can do but will still be challenging, instead of taking on somethign that they have done dozens of times before, unles that is all that is lieft to do. A good team member is one who also asks for help when needed, and offers and delivers help when asked. A good team member should be willing to give and receive constructive criticism, speak out when necessary, remain quiet when appropriate,  and accept when they are wrong about something with a certain amount of grace(not being bitter or pouting when their way/method or diea is not chosen or a better was is found). They should be a person that can understands that when one of the team learns a better way the whole team is enriched, and its the diffferences between us that should be celebrated not derided. A good team member also listens, as much or more, than they speak, and are willing to entertain other's ideas, particularly  when they are better than their own. A good team member will contribute to the success of every other team member, and celebrate individual wins, small and large as they would their own.
